## Domain decisions to follow (from the FE discussions)

**Auth & users**
- Exactly **one ADMIN**, created by an **idempotent seeder** from env vars (`ADMIN_NAME/EMAIL/PASSWORD` + optional center details); single admin enforced by a DB unique partial index. **No signup/registration endpoint, ever.**
- Roles are the enum `ADMIN` | `STUDENT`. Admin logs in with **email**; students log in only with **Student ID** (`S` + 9 digits, e.g. `S100000001`), never email. One login body `{ identifier, password }`; the BE decides by "contains @".
- Student ID: generated by the BE from an atomic counter (`STUDENT_CODE_START`, default 100000001), unique, **never reused** (even after delete). Internal ids are UUID strings returned as `id`; the Student ID is never used in URLs.
- The **admin types the student's initial password** (strong-password rule); `mustChangePassword` is true until the student changes it. Admin can reset it later (student detail milestone).
- `/auth/me` returns `{ user }` and restores the session on every page load; the admin user includes `centerName` (it signs the WhatsApp reminder message).
- Mobile app later: native clients can't use the cookie — a Bearer token option is an open question; don't break the cookie flow.

**Students**
- Fields: firstName, lastName, email (optional, lower-case, **unique among current students only**), `phone` (labelled "WhatsApp number"; **optional — if empty, save parentPhone**), parentName (required), `parentPhone` (required, "Parent WhatsApp number"), grade (Class 1–12), subjects (≥1 from the fixed list), monthlyFee (paise), joinDate. API field names stay `phone` / `parentPhone`.
- **Delete = discontinued = soft delete only** (`deletedAt`); no isActive field, no restore. Deleted students never appear in any list or count, can't log in, and GET/PATCH/DELETE on them → 404. Their payments/reminders/attendance stay. A returning student is added again with a new Student ID.
- Each student in the list includes **read-only `currentPayment`** (this month's status, latest payment date, method) derived from fee records — the Students API never sets payment data.
- List: server-side pagination, newest first, search by Student ID or name (partial, case-insensitive), filter by current-month payment status and payment date range.

**Fees / payments**
- **Monthly fee records** (one per student per month), created on demand; Total Fee defaults to the monthly fee (**pro-rated in the joining month**), Due Date to the admin's fee due day (default 10th; join date if later). Both editable per month.
- **Payments are recorded one by one** (amount, date not in future, method `CASH | UPI | BANK_TRANSFER | CARD | OTHER`) — never overwrite a paid total, **never delete or edit payments**. Paid amount = sum of payments.
- **The BE alone calculates** paidAmount, outstanding (= total − paid) and status: `PAID` (nothing outstanding) → `OVERDUE` (due date passed) → `PARTIAL` (something paid) → `PENDING`. "Today" in `APP_TIMEZONE` (Asia/Kolkata).
- Total fee can't go below what's paid (400); a payment can't exceed the outstanding amount (400).
- Fees list: one month at a time (month required), only current students who had joined by month end, same search/filters as Students.
- **No add/delete on the Fees API** — students are managed on the Students endpoints.
- Payment history: payments and reminders as **separate lists**, all months, newest first, with who recorded each payment.

**Payment reminders**
- Manual **WhatsApp click-to-chat** is done by the FE (`wa.me`) to the **parent's** WhatsApp number. The BE only **records** the initiation (`POST /fees/:feeId/reminders`) as status **`INITIATED`** — never marks it Sent/Delivered without proof, never sends anything itself.
- Allowed only while something is outstanding (else 409). **No daily limit** for manual reminders. Reminders exist only on the Fees side (never on Students).
- Automated reminders (email first, WhatsApp needs the Business API) are a **future** feature: schedule upcoming/due/1st/2nd overdue, no duplicate stage per month (unique partial index), skip paid months.

**Scope**
- **Batches are out of scope** — no Batch collection, fields, endpoints or logic unless the user brings them back.
- **Attendance is by class:** class (grade) + date → all current students of that class; one record per class per date (bulk upsert); `PRESENT` / `ABSENT`; no future dates. Built in the Attendance milestone.
- Out of scope for core: payment gateway, SMS, automated WhatsApp, file uploads, real-time, multi-tenant.

**Data conventions**
- Money in **integer paise**; date-only values as `"YYYY-MM-DD"` strings and months as `"YYYY-MM"`; UUID string `_id` exposed as `id`; enum values UPPER_SNAKE_CASE identical to the FE.
